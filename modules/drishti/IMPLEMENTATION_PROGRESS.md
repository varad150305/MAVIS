## Entry 2 — Local environment model for the web app (Environment State / Tracking / Hazard Engine / Priority Engine)

**What changed**: Generalized the on-device COCO-SSD detector (added earlier this session to triage Guardian Mode) into the structured pipeline the architecture calls for: `buildEnvironmentState()`, `updateTracking()` (centroid/IoU-based), `scoreHazard()` (deterministic risk formula), and `priorityAnnounce()` (dedup + interruption logic). Added `bboxClockPosition()`, `proximityFromBbox()` (bucketed VERY_CLOSE/CLOSE/MEDIUM/FAR with an explicit confidence tag — never an exact distance), and `isInPathCorridor()` (free-space heuristic).

**Why**: This is Phases 2/3/5/6/12/13 of the migration brief, generalized onto the one piece of local CV this project already had working (rather than being built from scratch) — object detection was already local; what was missing was a *structured, deterministic* layer between raw detections and speech output. Distance is deliberately never reported in exact units — see `ARCHITECTURE_AUDIT.md` §9 for why that would be dishonest given the actual method (bbox-area proxy, not real depth).

**Files modified**: `drishti-web/index.html` — new state (`environmentState`, `trackedObjects`, `nextTrackId`, `lastAnnouncedHazardKey/Time`), new functions inserted between the existing `drawOdOverlay()` and `startOdLoop()`, `odLoop()` updated to call the new pipeline each tick and to reflect `pathState` in the existing `#odPill` UI badge.

**How it works**:
- Every ~500ms tick (while the on-device detector is running), raw COCO-SSD detections are matched against the previous tick's tracked objects by class + IoU (>0.3 overlap), producing a `trackId`, `isNew` flag, and a rolling area history used to classify motion as `approaching`/`steady`/`receding`.
- Each detection in `HAZARD_CLASSES` gets a deterministic risk score = `objectRiskWeight(class) × proximityWeight × pathWeight × motionWeight`, thresholded into `LOW`/`MEDIUM`/`HIGH`/`CRITICAL`.
- `priorityAnnounce()` only speaks for `HIGH`/`CRITICAL` hazards, dedupes identical (object, clock-position) pairs within 8 seconds, and — deliberately — only runs while Guardian Mode is explicitly on, so this doesn't introduce new unsolicited voice interruptions beyond the toggle the user already controls.
- This is a genuine two-tier hybrid now: the **local** tier gives an instant "Stop, person approaching at your 12 o'clock" with zero network round-trip; the **existing cloud** tier (`handleGuardianProximity` → `guardianCheck`) still fires afterward for a fuller natural-language explanation. Local answers when it can; cloud fills in when local isn't enough — this is the core pattern the whole migration brief is asking for, now implemented for real in one vertical slice.

**How it was verified**: Two ways, both real (no fabricated numbers):
1. **Deterministic unit tests** (`test_hazard_engine.mjs`, run via headless-Chrome CDP against the actual running page, not reimplemented logic) — 20/20 passing, covering clock-position mapping, proximity bucketing, path-corridor detection, tracking continuity/motion classification, hazard scoring (including that a non-hazard class like "book" correctly scores nothing, and a close/centered person scores higher than a distant/corner one), priority-engine dedup, and the Guardian-mode gate.
2. **Full functional regression sweep** (`drive3.mjs`) — re-ran after this change: all 13 modes, Smart Live, Guardian toggle, wake word, large-text mode, voice-command parsing, history, chat, SOS, sharing — zero errors.

**Known limitations**:
- Proximity is a bounding-box-area proxy, not real depth — documented as such in the code comments and UI should eventually make this explicit to the user too (not yet done — see next step).
- Tracking is intentionally simple (centroid/IoU, no Kalman filtering) — will lose a track if an object is occluded for more than 2 seconds, or misassign IDs if two same-class objects cross paths. Acceptable per the brief's own "don't add unnecessary complexity" instruction, but worth stating plainly rather than implying it's more robust than it is.
- `HAZARD_CLASSES`/`objectRiskWeight` cover the COCO classes most relevant to a walking pedestrian (person, vehicles, bicycle, dog, chair/bench, fire hydrant, stop sign) — COCO's 80 classes don't include stairs, poles, curbs, or potholes, so real-world hazards outside this class list still rely entirely on the slower cloud safety-net poll, not the fast local path.
- This module exists only in the web app. The Flutter app has no equivalent yet (blocked on Entry 1's build verification, then requires `tflite_flutter` + a mobile detection model — see `ARCHITECTURE_AUDIT.md` §8).

**Next step**: once the Flutter build is confirmed working, port the object-detection + this same environment/hazard/priority logic (it's pure Dart-portable logic, no web-specific APIs involved) to the Flutter app using `tflite_flutter`.

## Entry 3 — Local color detection (web) + persisted test suite

**What changed**: Added `NAMED_COLORS` (a calibrated reference table of everyday color names — no false Pantone-style precision), `nearestColorName()` (luminance-weighted nearest-match), `_avgColorInRegion()`, and `localColorGrid()` (splits the last-captured frame into a 3×3 grid and reports distinct dominant colors by frequency). Wired into `snap()` for color mode: an instant local color read now posts to the chat log ("👁 Local read (no API call): mostly ...") before the cloud call even completes. Also moved the three test scripts written this session (`test_hazard_engine.mjs`, `test_color_engine.mjs`, `test_full_regression_sweep.mjs`) from the session scratchpad into `drishti-web/tests/`, with a `README.md` explaining how to run them, so they're a durable project asset rather than disposable session output.

**Why**: This is Phase 8 of the migration — the color mode currently calls Groq for even a trivial "what color is this" answer. A local average-color read is instant, free, and correct for the common case (one dominant color in frame); Groq is kept as the richer per-garment breakdown (classified Hybrid, not fully replaced, per `ARCHITECTURE_AUDIT.md` §5).

**Files touched**: `drishti-web/index.html` (new module after `capture()`; one integration point inside `snap()`), `drishti-web/tests/*` (new).

**How it was verified — including a real bug this caught**: Writing the first version of `nearestColorName()`'s reference table and testing it against pure primary/secondary colors (not just a couple of easy cases) surfaced a real calibration bug: pure green `(0,255,0)` mapped to "cyan" and pure blue `(0,0,255)` mapped to "dark blue" — the perceptual luminance weighting (blue channel weighted at 0.11, matching how human vision perceives brightness) interacted badly with the initial reference swatches. Recalibrated the table and re-verified against all 8 primary/secondary colors plus black/white/gray/brown before considering this done — this is exactly the kind of mistake that would have been embarrassing in a live demo ("it says grass is cyan") and was only caught by testing broadly rather than testing a couple of convenient cases. Final state: 16/16 tests passing (12 color-mapping checks + 4 grid-extraction checks, including that an empty/unpainted canvas returns an empty result rather than fabricating a color). Full regression sweep (`test_full_regression_sweep.mjs`) re-run afterward — still zero errors across the whole app.

**Known limitations**: This is whole-region color averaging, not object segmentation — it reports "what colors are present in each ninth of the frame," not "the shirt is blue and the pants are black" the way the cloud model can when asked. Lighting strongly affects the read (a white wall under warm indoor light will average toward tan/beige) — no white-balance correction is attempted, and none is claimed.

**Next step**: local OCR (Tesseract.js) — the other clearly local-first candidate (Phase 7) — has not been started yet.

## Entry 4 — Crossing-mode safety redesign, and a testing-harness bug that invalidated earlier "verified" claims

**What changed (the actual fix)**: Per `ARCHITECTURE_AUDIT.md` §7, redesigned Crossing mode from a GO/WAIT decision to an observation. The prompt now starts with `CLEAR_VIEW`/`UNCLEAR_VIEW` (self-assessed observation confidence only, never a crossing verdict), describes the signal/traffic/crosswalk, and is explicitly instructed never to tell the user to cross, wait, go, or stop. `showCrossingBadge()` no longer shows a SAFE/DANGER-style verdict — it always signals "your call" or "view unclear" and appends a fixed, **code-generated** disclaimer (`CROSSING_DISCLAIMER`) so it's present even if the model ignores the prompt. Also fixed a real bug this surfaced: `snap()`'s `speak(result)` call would have spoken the raw `CLEAR_VIEW`/`UNCLEAR_VIEW` token aloud (unlike `SAFE`/`DANGER`, not a natural spoken word) and wouldn't have included the disclaimer at all for a blind user who can't see the badge — fixed by constructing a mode-aware `spokenText` in `snap()`.

**Why**: The old prompt asked a general-purpose cloud VLM to make a life-safety GO/WAIT call from a single phone photo — neither that model nor this app's local CV can do that reliably, and the migration brief's own rules explicitly forbid it.

**Files touched**: `drishti-web/index.html` (prompt, `showCrossingBadge()`, `snap()`'s speech-construction), `drishti-web/tests/test_crossing_mode.mjs` (new).

**A more important finding, uncovered while testing this fix**: writing `test_crossing_mode.mjs` surfaced a bug in the *test harness itself* — one significant enough that it retroactively undermines confidence in earlier claims made this session. The mocked-Groq-response tests (`test_full_regression_sweep.mjs`, and its precursor `drive3.mjs`) intercept the app's `fetch()` call to `api.groq.com` via Chrome DevTools Protocol's `Fetch` domain. A cross-origin POST with a JSON body triggers a CORS **preflight OPTIONS request first** — `Fetch.requestPaused` fires for that OPTIONS request before it ever fires for the real POST. The harness was fulfilling that OPTIONS request with a plain 200 JSON response lacking `Access-Control-Allow-*` headers, which caused the browser to correctly treat the preflight as failed and silently block the real POST from ever being sent — the page's `fetch()` rejected with "Failed to fetch" every single time.

**Consequence**: because `snap()` catches its own errors internally and never crashes, this failure was invisible to a test that only checks for "no uncaught exception" — which is exactly what the regression sweep checks. **Every mocked test run today before this fix always hit the network-error catch path, never the success path.** Concretely: `showSafetyBadge()`, `showCrossingBadge()`, `parsePrices()`, and `showTextPanel()` being rendered correctly with real mocked content was never actually verified earlier in this session, despite being reported as passing — only "the app doesn't crash when Groq is unreachable" was actually being tested.

**Fix applied and re-verified**: both test files now handle the OPTIONS preflight separately (204 response with proper `Access-Control-Allow-Origin/Methods/Headers`) before fulfilling the real POST (also now including `Access-Control-Allow-Origin`). Re-ran everything after the fix:
- `test_crossing_mode.mjs`: 10/10 passing, now genuinely exercising the CLEAR_VIEW/UNCLEAR_VIEW/malformed-response paths.
- `test_full_regression_sweep.mjs`: still zero issues, but now the success-path rendering code is actually running for the first time. Spot-checked content correctness directly (not just "no crash"): Safety mode correctly renders `✅ SAFE` with the right detail text; Prices mode correctly parses `Amazon ₹499` / `Flipkart ₹520` into the price grid.
- `test_hazard_engine.mjs` (20/20) and `test_color_engine.mjs` (16/16) were never affected by this bug — they test pure local logic with no network dependency at all.

**Known limitations**: This was caught because a *new* test (crossing mode) happened to check the actual rendered badge state, not just "did it crash." The lesson: a driven-browser test that only watches for uncaught exceptions can pass while silently never exercising its intended code path — content assertions, not just crash detection, are necessary. Worth re-auditing if any future test is added in "no crash" style only.

**Next step**: local OCR remains the next unstarted item.

## Entry 5 — Local OCR (Tesseract.js)

**What changed**: Added `loadOcrWorker()` (lazy-loads Tesseract.js from CDN and creates a persistent worker — only when the user opens Read Text mode, not on page load) and `localOCR(imgSource)`. Wired into `snap()`: for `text` mode, local OCR runs first; its result is used (and the Groq call is skipped entirely) only if Tesseract's own confidence score is ≥65 and it recognized at least 3 characters — otherwise it falls back to the existing cloud call, same as before this change.

**Why**: Read Text is one of the most-used modes and was previously 100% cloud-routed for every single request, even a clear, high-contrast printed sign that a local OCR engine handles well. The confidence floor matters: Tesseract is materially weaker than the cloud VLM on angled, handwritten, or low-contrast text, so trusting a low-confidence local read (or worse, speaking it aloud as fact) would be a regression, not an improvement — falls back to cloud instead of guessing, per this project's own rule.

**Files touched**: `drishti-web/index.html` (new module after `localColorGrid()`; `setMode()` triggers lazy-load; `snap()`'s text-mode branch), `drishti-web/tests/test_ocr_engine.mjs` (new).

**How it was verified — genuinely, not mocked**: This is the one local-CV feature this session that isn't pure deterministic logic, so it was tested by actually running the real OCR engine, not by asserting against a stub. The test renders real text ("HELLO WORLD") onto the app's own capture canvas using the Canvas API, then calls the real `localOCR()` function on it. Result: Tesseract genuinely read it back correctly with a confidence score above the app's own threshold. A second check — a blank white canvas with no text — confirmed OCR returns near-empty output rather than fabricating text, which is what makes the confidence-gated fallback behave correctly. 5/5 passing. Full regression sweep re-run afterward — still zero issues.

**Known limitations**: Tested against clean, computer-rendered, high-contrast text at a large font size — the easy case. Real-world performance on a phone photo of a curved product label, dim lighting, or handwriting has not been measured (would need real test images, not canvas-rendered text, to evaluate honestly — flagged as future work for the evaluation framework, not claimed as tested here). The 65% confidence threshold is a reasonable starting point, not a tuned value — revisit once real-world accuracy data exists.

**Next step**: currency recognition (the honestly-scoped OCR+heuristic hybrid from `ARCHITECTURE_AUDIT.md` §9) and the performance/evaluation framework remain.

## Entry 7 — Local currency recognition (OCR + color heuristic)

**What changed**: Added `CURRENCY_DENOMINATIONS`, `CURRENCY_COLOR_HINTS` (real Mahatma Gandhi New Series note colors per denomination), `extractDenomination()` (word-boundary regex counting how many times each valid denomination number appears in OCR text — requires 2+ occurrences, since a real note prints its denomination in several places while a random OCR misread of a serial number is a one-off), and `localCurrencyRead()` (combines OCR + `localColorGrid()`, only reports `HIGH` confidence when both agree). Wired into `snap()` for currency mode: used only at `HIGH` confidence, cloud fallback otherwise — same pattern as OCR and color mode.

**Why**: Per `ARCHITECTURE_AUDIT.md` §9, no trained Indian-currency classifier exists or could be honestly built without labeled training data this project doesn't have. This is explicitly a heuristic (OCR reads the printed number, color cross-checks it), not a classifier presented as more than it is — and it's designed to fail safe: a lone signal (right number, wrong color, or vice versa) is deliberately treated as insufficient (`MEDIUM`, not `HIGH`) and falls back to the cloud model rather than guess.

**Files touched**: `drishti-web/index.html` (new module after `localOCR()`; `setMode()` now lazy-loads OCR for currency mode too; `snap()`'s currency branch), `drishti-web/tests/test_currency_engine.mjs` (new).

**How it was verified**: 10 tests — pure-logic checks (denomination extraction correctly ignores random text, correctly avoids treating a single serial-number-like digit match as valid, correctly disambiguates ₹100 from ₹1000 via word boundaries, correctly picks the most-frequent candidate when multiple denominations' digits appear), color-hint sanity checks against the real note colors, and — genuinely, not mocked — two full-pipeline runs through the real OCR engine: a canvas painted gray with "500" printed three times (matching color + number → correctly `HIGH` confidence) and the same text on a red background (mismatched color → correctly demoted to `MEDIUM`, meaning the app would fall back to the cloud model rather than state a denomination with unwarranted confidence). 10/10 passing. Full regression sweep re-run afterward — still zero issues.

**Known limitations**: Tested against clean, computer-rendered mock "notes," not real photos of actual currency — real Indian notes have watermarks, security threads, and worn/creased surfaces that will affect both OCR accuracy and the color read in ways not exercised here. The color-hint table is a reasonable approximation of each denomination's dominant color, not calibrated against real note photos. This is the last of the four features (object detection, color, OCR, currency) originally scoped for local-first treatment on the web app.

## Entry 10 — Real Groq API key testing uncovers a genuine production bug (fake keys could never have caught this)

**Context**: the user reported seeing a "no Groq API key" message despite having entered one, then provided a real Groq API key directly to unblock testing. All testing up to this point in the session used a fake key (`gsk_fake_test_key`), which fails at the auth check before ever reaching real response-parsing code — meaning **the actual shape of a real model's output had never been exercised**, by design of how the testing was scoped. Using a real key immediately surfaced a real, serious bug within the first request.

**What was found**: the app's automatic model-fallback logic (pre-existing, not new this session — see `_isModelAccessError` in `callGroq()`) correctly detected that `meta-llama/llama-4-scout-17b-16e-instruct` is not accessible to this account (`model_not_found`, verified directly against the Groq API), and fell back to `qwen/qwen3.6-27b` as designed. But that model is a **reasoning model** — it emits internal chain-of-thought wrapped in `<think>...</think>` before its actual answer, and:
1. The raw `<think>` reasoning text was being sent straight to the user (as the "description," to be spoken aloud) — completely unusable and confusing output.
2. At the app's existing `max_tokens: 600` (tuned for a normal, non-reasoning model), the reasoning alone consumed the entire budget, so the response was truncated *before the model ever produced an answer* — every single request returned nothing useful.

**Root-caused with real API calls, not guesswork**:
- Confirmed `llama-4-scout` returns `model_not_found` for this account (direct `curl` test).
- Confirmed `qwen/qwen3.6-27b` genuinely supports vision (`input_modalities: ["text","image"]` from Groq's own model-info endpoint) — this isn't a broken/wrong fallback choice, just a much "slower-thinking" model than the app was tuned for.
- Confirmed Groq's `reasoning_format: 'hidden'` parameter works for this model (verified: with it, the response is either a clean answer or empty — never raw `<think>` text) but does **not** reduce how many tokens the model spends reasoning internally — it just stops those tokens from appearing in the visible output.
- Calibrated the real token requirement empirically: the app's actual `describe` prompt + a real test image needed **1,313 completion tokens** (reasoning + answer combined) to complete naturally (`finish_reason: 'stop'`) with a correct, on-topic description. At `max_tokens: 600` and even `2000`, it was truncated with zero usable output every time.
- **A serious secondary constraint surfaced in the process**: this Groq account/tier has an **8,000 tokens/minute rate limit**. A single reasoning-model request can use 1,300-2,000+ tokens, meaning only a handful of vision requests can be made per minute before hitting `429 rate_limit_exceeded` — confirmed by hitting it directly during calibration testing.

**Fixes applied**:
1. Added `reasoning_format: 'hidden'` to every Groq request (`_sendGroqRequest`).
2. Raised `max_tokens` from `600` to `3000` (roughly 2x the empirically-observed real requirement, balanced against the rate-limit constraint above — not raised further despite the model's 16,384-token ceiling, since that would make the rate limit bind even tighter).
3. Added `stripReasoning()` as a defensive second layer — strips any `<think>...</think>` block (or an unclosed one, for the truncated-mid-thought case) from the final content — so even if a future model/response doesn't respect `reasoning_format`, raw reasoning can never reach the user. Applied at both places `callGroq()` returns a result (the normal path and the auto-fallback retry path).
4. Empty/reasoning-only responses now return a clear "The model's response was incomplete — please try again" message instead of either raw gibberish or a bare "No response."

**Files touched**: `drishti-web/index.html` (`_sendGroqRequest`, `stripReasoning()`, both `callGroq()` return points).

**How it was verified — with real API calls, spending real quota deliberately and minimally**: after the fix, ran the actual app's `describe` mode against the real Groq API with a real test image — got a correct, complete, natural description (verified by direct calibration call: `finish_reason: 'stop'`, sensible on-topic content matching the test image). A subsequent verification attempt through the full app hit the account's rate limit from the cumulative token usage of this same debugging session (confirmed via a direct `callGroq()` call surfacing the real `429` error) — this is the rate-limit constraint above, not a new bug, and no further real API calls were made afterward specifically to conserve the user's quota. The full mocked-key regression sweep (67 tests + full sweep) was re-run afterward and remains clean — this fix doesn't touch any of that code path differently.

**Known limitations / important context for the user**:

## Entry 12 — Two real bugs surfaced by actual live usage (found by the user, not by testing)

After the key was finally saved correctly, the user reported a continuous wall of `429 Rate limit` errors during real use — far more than expected. Two genuine, distinct bugs, both pre-existing (not introduced this session's earlier entries), were found and fixed.

### Bug 1 — Guardian Mode's cooldown didn't actually cool down

**The bug**: `lastGuardianAlert` (the timestamp gating `guardianCheck()`'s cooldown) was only updated inside the `if(rating==='DANGER'||rating==='CAUTION')` branch — i.e., only on an actual alert. If the cloud model rated a scene `SAFE`, or if the call errored (a `429`, a network blip, anything), the cooldown timestamp never advanced. Combined with `handleGuardianProximity()` calling `guardianCheck()` unconditionally on every ~500ms detection tick whenever a hazard-class object stayed in frame, this meant: point the camera at a person or chair for more than a few seconds with Guardian Mode on, and the app would fire a fresh real Groq request on almost every tick, bounded only by how fast each network round-trip completed — not by the intended 6-second cooldown at all.

**Why it only showed up now**: earlier in the session, every test used a fake key that failed at the auth check before this code path could ever run for real, and even after the real key started working, testing was mostly single manual snaps, not sustained Guardian-mode camera pointing. Live usage was the first scenario that actually exercised this.

**The fix**: introduced `lastGuardianAttempt`, updated at the start of every actual attempt (success, `SAFE`, or error alike) — the cooldown now gates on this, not on `lastGuardianAlert` (which still separately tracks "last time we actually alerted," unused elsewhere but kept for clarity). Also widened `GUARDIAN_MIN_MS` from 6 seconds to 45 seconds, since real per-call cost is now known (the qwen fallback model can use 1,300-7,000+ tokens per call against an 8,000 tokens/minute account budget — a call every 6 seconds could alone exceed the entire budget). `handleGuardianProximity()` also now short-circuits immediately if still within the cooldown, instead of doing the detection-scanning work every tick regardless.

### Bug 2 — The truncation-retry and model-fallback failure paths didn't reuse the rate-limit message parsing

**The bug**: the primary request-failure path correctly parses Groq's `429` body for a real wait time (Entry 11). **The fix**: extracted the response-to-error-message logic into `_throwForFailedResponse()`, used consistently at all three failure points (primary, retry-after-truncation, and alt-model-fallback).

**Files touched**: `drishti-web/index.html` (`guardianCheck()`, `handleGuardianProximity()`, `callGroq()`, new `_throwForFailedResponse()`), `drishti-web/tests/test_resilience.mjs` (2 new tests).

## Entry 13 — Long responses were only partially spoken (real usage found this too)

**The report**: "it also does not read the entire thing that comes in chat it reads the first few lines then directly goes to the end."

**Two real, separate bugs, both pre-existing**:
1. **Chrome's Web Speech API bug** (used whenever no Sarvam key is configured, which is the default): a single long `SpeechSynthesisUtterance` silently stops after roughly 15 seconds of speech in Chrome — a long-documented browser bug, not something this app did wrong per se, but the app never worked around it. A multi-sentence Groq description easily exceeds 15 seconds at the app's speech rate, so it would just go quiet partway through with no error.
2. **Sarvam's actual 500-character request cap** (if a Sarvam key is configured): the old code did `text.slice(0,500)` and sent only that — anything past the first ~500 characters was silently discarded, never spoken, with no sign anything was missing.

**The fix**: `splitIntoSpeechChunks(text, maxLen)` splits text into sentence-complete chunks (not a blind character cutoff, so playback still sounds natural) at both TTS layers. `speakWebSpeechChunks()` chains multiple short utterances via `onend` — each one finishes well under Chrome's ~15s bug threshold. The Sarvam path now loops through 500-char chunks making one request per chunk and chaining playback via `audio.onended`, and — since the whole point was "don't silently drop content" — a Sarvam failure partway through now falls back to Web Speech for the *remaining* text instead of just stopping.

**A new risk this introduced, caught before shipping**: chaining playback via `onend`/`onended` callbacks means a `stopSpeaking()` call (e.g., the user says "stop", or a new `speak()` call interrupts an old one) needs to actually stop the *whole chain*, not just the current chunk. Chrome's `speechSynthesis.cancel()` still fires the interrupted utterance's own `onend` event, which — naively — would have resumed the "stopped" chain and kept talking. Fixed with a generation-token pattern: every `speak()`/`stopSpeaking()` call bumps `speechGeneration`, and every chain-continuation callback checks it's still the active generation before proceeding, silently aborting if a newer call or an explicit stop has superseded it.

**Files touched**: `drishti-web/index.html` (`splitIntoSpeechChunks()`, `speak()` rewritten, new `speakWebSpeechChunks()`, `stopSpeaking()`), `drishti-web/tests/test_speech_chunking.mjs` (new).

**How it was verified**: `tests/test_speech_chunking.mjs` — confirmed long text actually splits into multiple chunks (and a larger max length produces fewer chunks, as expected); confirmed no words are lost across chunk boundaries; confirmed text with no sentence-ending punctuation still returns a usable single chunk rather than crashing; confirmed **all** chunks get queued as separate utterances, not just the first (the actual fix for the reported bug), with the completion callback firing exactly once at the end, not per chunk; and — simulating the real Chrome cancel-still-fires-onend behavior — confirmed a superseded generation stops after its current chunk and does not queue the rest or fire the completion callback twice. 8/8 passing. Full regression sweep and the rest of the suite re-run — zero issues.

**Known limitations**: chunk boundaries are sentence-based via a simple regex (`[^.!?]+[.!?]+`) — text with unusual punctuation (ellipses, abbreviations like "Dr." or "₹1.50", decimal numbers) could split at an odd point sometimes. Not expected to break anything (each chunk still gets spoken as valid text), just an occasional slightly awkward pause. Not evaluated with real Sarvam audio (no Sarvam key was available this session) — the chunking and chaining logic is verified, but real chained-audio playback quality (any gap or click between chunks) hasn't been listened to.

**Important correction — this entry alone did NOT fully fix the reported bug.** See Entry 14: a second, separate bug (a proactive follow-up message interrupting the main description) was still cutting speech short after this fix shipped. Both were real; fixing only this one was insufficient.

## Entry 14 — The actual, complete root cause of "reads a few lines then jumps to the end"

Entry 13's chunking fix was real and necessary, but the user reported the exact same symptom again after it shipped. Live-testing with the real key (not mocks) found the true, complete cause.

**What was actually happening**: `snap()` has a proactive feature — if a description mentions anything read/written (checked via a regex including the word `reads?`), it offers to speak "I can see text in the image, say read it" after the description. This follow-up was scheduled with `setTimeout(fn, Math.min(result.length*60, 8000))` — a **guessed** delay, capped at 8 seconds, and scheduled **before the main description's own `speak()` call even ran** in the code. A real live test confirmed the actual failure mode directly: a 426-character, 4-sentence description (which itself contained the word "reads" — e.g. "a timestamp that reads...") takes well over 8 seconds to actually speak once split into multiple chunks (Entry 13's own fix). The follow-up's timer fired mid-description, called `speak()` again, and since every `speak()` call stops whatever's currently playing first, the main description was cut off partway and replaced by the short follow-up message — which is exactly what looked like "reads the first few lines then jumps to the end."

**The fix**: `speak()` now accepts an optional `onSpeechDone` callback, invoked exactly when the entire chunk queue genuinely finishes (built on Entry 13's own completion-tracking, not a new mechanism). `snap()` now passes the "I can see text" follow-up as this real callback instead of a guessed timer, and the whole block was moved to *after* the main `speak(spokenText, followUp)` call in the code, not before it. The follow-up can now only ever start once the description has actually finished, regardless of how long that takes.

**Files touched**: `drishti-web/index.html` (`speak()` signature, `snap()`'s follow-up logic reordered), `drishti-web/tests/test_followup_timing.mjs` (new).

**How it was verified**: `tests/test_followup_timing.mjs` — mocked `speak()` to take a realistic ~3 seconds to "finish" (instead of resolving instantly, which would never have exposed this bug) and fed it a real describe-mode response containing the word "reads," through the actual `snap()` code path. Confirmed exactly 2 speak calls occur (main description, then follow-up — not the description getting cut off partway by a third), confirmed the main description is spoken in full before anything else starts, and confirmed the follow-up's start time is measured *after* the mocked description's own completion, not on a fixed guess. 4/4 passing. Full regression sweep re-run — zero issues.

**Also checked**: grepped for every other `setTimeout(()=>speak(...))` pattern in the codebase — the only two other instances (a camera-ready announcement and an app-ready announcement, both one-off startup messages with nothing else speaking at that point) are unrelated to this bug and don't need the same fix.

## Entry 15 — Client-side rate-limit budget tracking (making the constraint visible instead of a surprise)

The account-level rate-limit constraint (Entry 10-14) can't be fixed in code, but the *experience* of hitting it repeatedly and unpredictably can be improved. The user reported it was "causing too much trouble."

## Entry 21 — Two real functional bugs, found by code review + real Tesseract testing: voice commands failing silently, and OCR confidently reporting incomplete reads

The user reported, separately from all the visual work: "it does not work good when i give voice commands it does not even listen properly and it does not read correctly what is written in front of it." Both investigated by finding and reproducing an actual root cause, not by guessing at UI polish.

### Bug 1 — Voice commands fail completely silently when the camera isn't running

**Root cause**: `handleCmd()`'s main dispatch loop (for both the English `CMD_MAP` and the regional-language `REGIONAL_CMDS`) had `if(cmd.mode) setModeVoice(cmd.mode); else if(cmd.snap && stream) snap();` — `setModeVoice()` sets the mode pill and then only calls `snap()` internally if `stream` exists, and does nothing else if it doesn't. So a perfectly-recognized command like "describe" spoken while the camera is stopped (or before it's ever been started) matched its regex, ran, and produced **zero output of any kind** — no sound, no message, nothing. Every other special-cased command in the same function (street navigation, crossing check, translate, gesture) already had a `stream` check with a spoken "Start the camera first" fallback; this specific code path was the one place that didn't, making the failure invisible rather than explained. For a blind user with no visual mode-pill feedback to notice, this looks exactly like "voice commands don't work at all."

**Also found while investigating**: a second, related issue that made the *first few seconds after opening the app* — exactly when someone is most likely to try their first voice command — worse than necessary. On a return visit with camera/mic permission already granted, the app auto-starts the camera (`tryAutoStart()`) and speaks "Camera is ready...". Completely independently, a fixed `setTimeout(..., 800)` at the bottom of the script unconditionally speaks "Drishti is ready. Start the camera..." if a Groq key is saved — with no check for whether the camera had already auto-started. On most real return visits both fire back-to-back: since every `speak()` call interrupts whatever's currently playing, the user hears a garbled overlap of two announcements instead of one clear one, one of which gives wrong advice ("start the camera" when it's already running) — and voice commands stay paused (`vcPaused`, which mutes the command mic while Drishti is talking, so it doesn't hear its own voice) for the combined duration of both.

**The fix**: added `if(!stream){ speak('Start the camera first.'); return; }` (and the Hindi equivalent, `'Pehle camera shuru karein.'`) to both dispatch loops, right before the mode/snap branch. Also gated the generic startup announcement on `if(!stream)` at the moment its timer fires, so it's skipped entirely on the very common case where the camera already auto-started by then.

**Files touched**: `drishti-web/index.html` (`handleCmd()`'s `CMD_MAP` and `REGIONAL_CMDS` loops; the bottom-of-script startup announcement), `drishti-web/tests/test_voice_cmd_feedback.mjs` (new).

**How it was verified**: `tests/test_voice_cmd_feedback.mjs` — drives the real `handleCmd()` function directly (not a mock) with the camera genuinely stopped via the real `stopCam()`, confirms an English mode command, a Hindi mode command, and a generic mode-less "take a photo" command all now produce real spoken feedback instead of silence, and confirms (with the camera genuinely started via the real `startCam()`) that a normal command still switches mode correctly with no false-positive "start the camera" message. 4/4 passing. One real complication surfaced while writing this test and worth recording: an early version raced against real headless-Chrome speech-synthesis timing and was flaky because `vcPaused` genuinely does stay true for however long the startup announcement(s) take to finish speaking — which is itself a real illustration of the exact problem being fixed, not a test bug to route around blindly; the test now explicitly controls `vcPaused` so it deterministically tests the dispatch-loop fix in isolation from that separate, already-documented speech-timing mechanism. Full regression sweep re-run afterward — zero issues.

**Known limitations**: this fixes the *silent* failure specifically. Voice recognition accuracy itself (whether Chrome's speech-to-text correctly transcribes a given accent/phrase) can't be verified in this sandboxed environment at all — there's no real microphone or audio path available to headless/automated Chrome here, so this class of issue has never been testable this session and isn't claimed to be fixed, only the silent-failure-when-camera-is-off case that was actually found and reproduced.

### Bug 2 — Local OCR can report high confidence while having silently dropped words

**Root cause, found by deliberately testing against a realistic degraded image (not just clean canvas text)**: rendered a two-line sign ("EXIT ONLY - DO NOT ENTER" / "Emergency use fine 500 rupees") with mild rotation, uneven lighting, and blur — a plausible stand-in for a real handheld photo of a sign in imperfect light — and ran it through the real Tesseract.js engine already used in this app. Result: **94% reported confidence**, while the actual recognized text was `"EXIT ONLY - DO\nEmergency use fine 500"` — entire trailing words ("NOT ENTER", "rupees") were silently absent, not mis-recognized. Tesseract's confidence score reflects confidence in the text it did manage to recognize; it has no signal at all for text it failed to detect in the first place, so a confidently-read-but-incomplete result sails straight past a pure confidence threshold. At the app's `OCR_CONFIDENCE_THRESHOLD=65`, and even well above it, this reached the user as the final "reading" — for a sign about *not entering*, dropping exactly that clause is a genuinely bad failure mode, not a cosmetic one. Follow-up testing found this reproduces reliably on multi-line/rotated composited text but not on single-line horizontal text at the same degradation levels — line count is the cheapest available signal that a read might be incomplete.

**The fix**: two changes, both evidence-based rather than arbitrary. (1) `OCR_CONFIDENCE_THRESHOLD` raised from 65 to 80 — verified via direct testing that heavily-garbled/unrecognizable text scores 0-41 while genuinely clean text scores 90-100+, so 80 keeps real margin without needing a lower bar (this alone would *not* have caught the 94%-confidence bug above — it's a separate, complementary tightening). (2) `localOCR()` now also returns `lines` (Tesseract's own recognized line count), and the text-mode shortcut in `snap()` now additionally requires `local.lines<=1` before trusting the local read over the cloud model — multi-line output no longer self-certifies via confidence alone; it always falls through to the cloud model instead. This deliberately keeps the fast local path for what it's actually good at and most commonly used for (a short sign, a price tag, a room number — one line, quick, no API call needed) while routing anything with more surface area for a silent drop to the more capable cloud model, consistent with the project's existing "don't guess, fall back when uncertain" rule already applied to color and currency.

**Files touched**: `drishti-web/index.html` (`OCR_CONFIDENCE_THRESHOLD`, `localOCR()`'s return shape, the text-mode gate in `snap()`).

**How it was verified**: re-ran the exact reproducing test after the fix — `localOCR()` now reports `lines:2` for that same degraded two-line image, which the new `<=1` gate correctly rejects (falls through to cloud instead of trusting the incomplete 86-94%-confidence read). Existing `test_ocr_engine.mjs` (5/5) and `test_currency_engine.mjs` (10/10, since currency shares the same confidence constant) both still pass unchanged, confirming the tightened threshold doesn't break the clean-text path. Full regression sweep re-run — zero issues.

**Known limitations**: this specific fix targets the exact failure mode reproduced (multi-line composited text under mild degradation); it is not a general guarantee that local OCR is now always complete — a single-line read could theoretically still drop a word at either end without tripping this particular signal, though testing at several degradation levels on single lines only ever produced either a clean read or an appropriately low confidence score, never the confident-and-incomplete combination found on multi-line text. All local-OCR testing this session (before and after this fix) uses synthetic canvas-rendered/degraded images, not real phone photos — real-world accuracy on actual handheld photos remains genuinely unmeasured, as already noted in Entry 5.

## Entry 24 — "Request too large": a genuinely different failure the app was mishandling, found from a real user-pasted error

Immediately after Entry 23 shipped, the user reported it "keeps on showing rate limit," pasting Groq's raw error verbatim: `Request too large for model qwen/qwen3.6-27b ... Limit 8000, Requested 9805, please reduce your message size and try again.`

**Why this is a genuinely different bug, not the same rate limit already handled**: every previous rate-limit fix in this project (Entries 10-15, 22) assumed the failure was *time-based* — the account's rolling per-minute usage was exhausted, and waiting resolves it. This error is *size-based*: the prompt tokens plus the `max_tokens` the app itself requested for this one call already exceed the account's entire 8,000-token ceiling, before any rolling usage is even considered. Waiting doesn't help even slightly — the identical request fails identically forever. The old code didn't distinguish the two: `_throwForFailedResponse()` only special-cased HTTP 429 by trying to parse a "try again in Xs" phrase, and this message has none, so it fell through to a generic, actively wrong `'Rate limit — please wait a moment and try again.'` — meaning every time this error occurred, the user was told to do the one thing guaranteed not to work, which explains "it keeps on showing rate limit" (the user very reasonably waited and retried, repeatedly, because that's what the message told them to do).

**The real fix — using the numbers Groq's own error already gives us, not a guess**:
1. `_parseTooLargeError(msg)` extracts `Limit` and `Requested` directly from the message text.
2. New `_requestWithSizeGuard(model, msgs, maxTokens)` wraps `_requestAndParse()`: on a "too large" failure, it computes the real prompt-token cost as `Requested - maxTokens` (both numbers are exact, from Groq, not estimated) and retries **once** with `max_tokens` trimmed to `Limit - promptTokens - 100` (a small safety margin) — precisely as much room as actually exists, not a blind smaller guess. If even that trimmed budget would be too small to be useful (<200 tokens), it doesn't bother retrying and lets the normal failure path report it honestly instead. Replaces all 4 of `_callGroqOnly()`'s `_requestAndParse()` call sites (primary attempt, both alt-model-fallback attempts, and the truncation-retry attempt), so every path that could hit this gets the same protection.
3. `_throwForFailedResponse()` now checks for this specific error shape *before* falling through to the generic 429 handling, and gives an honest message: waiting won't help, try a shorter question or check the account's tier — instead of the misleading "wait a moment."
4. The Gemini-fallback wrapper from Entry 23 now also treats "too large" as a trigger condition (alongside "rate limit"/"quota is low") — this is actually the best possible candidate for the fallback, since it's a Groq-account-specific ceiling that a completely separate Gemini account isn't bound by at all.
5. Secondary mitigation: trimmed the chat Q&A history sent with every question from the last 3 exchanges (6 messages) to the last 2 (4 messages), on both Groq and Gemini — reduces how often accumulated conversation context pushes a request over the edge in the first place, without eliminating the need for the real fix above.

**A second, real bug caught while building the fix, not a hypothetical one**: the first version of `_requestWithSizeGuard()` read the failed response's body directly (`attempt.res.json()`) to check for the "too large" shape. A `Response` body can only be read once — every *other* caller downstream (`_throwForFailedResponse()`, called with just `res` at three of the four call sites) also needs to read that same body to get the real error message. Concretely, this silently broke the *existing, working* rate-limit-wait-time feature from Entry 11: any 429 that wasn't the "too large" shape would have its message silently emptied out by the first (now-consumed) read, degrading a specific, useful "wait about 43 seconds" message down to the vague fallback — caught immediately by `test_resilience.mjs` going from 11/11 to 9/11 the moment this was tested, not discovered later. Fixed by reading via `.clone()` so the original response body remains untouched for whoever reads it next.

**Files touched**: `drishti-web/index.html` (`_parseTooLargeError()`, `_requestWithSizeGuard()`, all 4 `_requestAndParse()` call sites in `_callGroqOnly()`, `_throwForFailedResponse()`'s 429 branch, `callGroq()`'s Gemini-fallback trigger regex, chat history slice length in both `_callGroqOnly()` and `callGemini()`), `drishti-web/tests/test_too_large_request.mjs` (new).

**How it was verified**: `tests/test_too_large_request.mjs` reproduces the user's exact error message verbatim via CDP `Fetch` interception (not a paraphrased or simplified version) on the first request, and confirms: exactly 2 requests occur (the failure and one corrected retry), a system message explains what happened, the retry succeeds and its result reaches the screen, and — the most precise check — the retry's actual `max_tokens` is exactly **1095** (`8000 - (9805-3000) - 100`), matching the hand-computed value exactly rather than just "some smaller number." A second check confirms `_throwForFailedResponse()` never says "wait a moment" for this error shape and does explain the real cause. 6/6 passing. The clone-related regression was caught and fixed via `test_resilience.mjs` (back to 11/11). Full regression sweep and the entire deterministic suite (119 tests total) re-run clean on a fresh Chrome instance afterward; `test_auto_retry.mjs` showed the same already-documented tab-accumulation flakiness when run 11th-in-sequence with many other files in one long-lived browser session (2/4), confirmed clean (4/4) in isolation — unrelated to this change, same root cause already established in Entry 22.

**Known limitations**: the size-guard's one-retry-then-give-up behavior means an extremely large single request (e.g., a very long chat history plus a large image, where even the trimmed budget would be under 200 tokens) still fails outright rather than being trimmed further — judged a reasonable line given the project's "one retry, never loop" principle (Entry 12, Entry 22), but a request that's *that* oversized would likely need actual content trimming (shorter prompts, smaller images), not just a smaller answer budget, which this fix doesn't attempt. The Gemini-fallback trigger broadening (adding "too large" as a condition) was verified by code review and the existing Entry 23 end-to-end test infrastructure, not by re-running the full real-key end-to-end test specifically for this new trigger condition — the underlying `callGemini()` call path is identical either way, so this is a reasonable inference rather than a fully independent verification.

## Entry 28 — Proactive client-side Gemini budget tracking, a local-OCR fallback for total cloud failure, OCR preprocessing, and a real bug this session's own testing caught

The user reported, again: "it keeps on rate limiting," both providers, plus "it is not reading text properly" and "many other flaws." Entry 27 already established both providers are genuinely, simultaneously exhausted today — real resource exhaustion, not fixable by more error-message parsing. Given that ceiling, the honest next move is: (1) stop wasting requests against a quota already known to be dead, and (2) stop leaving the user with literally nothing when every cloud option is gone, since local OCR is sitting right there having already done partial work on every text-mode snap.

### Proactive Gemini daily-budget tracking (skip-when-exhausted)

**What changed**: `geminiBudget` (`{date, used}`, persisted to `localStorage` under `dk_gemini_budget`, resetting on local-date change) now tracks every real Gemini request this browser makes toward the real 20/day ceiling Entry 27 found. `callGroq()`'s wrapper checks `geminiBudgetExhausted()` *before* even attempting Gemini — once today's local count reaches 20, it goes straight to `_callGroqOnly()` instead of making a request already known to fail, and says so via a system message. `callGemini()` also reacts to Google's own response: if a 429 body's quota metric name contains `PerDay` (the exact shape from Entry 27's real capture), the local counter is immediately forced to the exhausted state regardless of what our own count was — covering the case where usage happened outside this browser (other tabs, other sessions) that our local count couldn't have known about. A new header pill (`#geminiBudgetPill`, styled identically to the existing Groq budget pill) shows "✨ Gemini N/20 today" so the constraint is visible instead of a surprise discovered one 429 at a time.

**Why this is a real improvement even though it can't lift the actual quota**: Entries 10-27 collectively spent a lot of effort making *individual* rate-limit failures easier to understand after they happen. This is the first piece that avoids *causing* some of them — a request against a quota this session already knows is empty is pure waste: it costs the user a full round-trip of latency, and depending on exact provider behavior, may or may not even count differently against the quota than a smart client-side skip would. Tracking is only ever approximate (Google's actual per-project daily reset time isn't exposed to a client), which is why the reactive per-response correction exists alongside the proactive local count — either signal alone would miss the other's case (a fresh page load doesn't know about quota used by a different tab; a slow-to-notice local count could lag a real quota that was already exhausted moments ago elsewhere).

### Text mode: a local OCR read now survives total cloud failure

**The gap**: text mode's local Tesseract.js attempt (Entry 5, tightened in Entry 21) only *replaces* the cloud call above `OCR_CONFIDENCE_THRESHOLD` (80) and single-line output — anything less confident or multi-line still fell through to the cloud model, as designed. But if the cloud call then failed too (exactly the live state described in Entry 27), the local OCR attempt's result was simply discarded and the user got nothing but an error message — even though Tesseract had already produced *some* real text moments earlier in the same `snap()` call. For "not reading text properly" under today's real rate-limit conditions, this is likely a meaningful part of what's being experienced.

**The fix**: `snap()` now keeps the local OCR attempt (`localOcrCaveat`) around, declared outside the `try` block so it's still reachable from `catch`, whenever local OCR produced at least 3 characters of text but didn't clear the strict gate. If the subsequent cloud call throws, text mode now shows that local read instead of a bare error — honestly framed ("cloud reading failed... showing a local read instead... may be incomplete") in both the on-screen system message and what gets spoken, never presented as equivalent to a confirmed cloud transcription.

**A real bug this session's own testing caught, not a hypothetical one**: the first version of this fix declared `let localOcrCaveat=null` *inside* the `try` block. JavaScript's `try{}` and `catch(e){}` are separate block scopes, so the `catch` block's reference to `localOcrCaveat` was a `ReferenceError` — meaning the very first real test of this path threw an *uncaught* exception out of `snap()`'s own error handler, which would have been strictly worse than the original bug (silent failure instead of an honest error message) for anyone hitting a cloud failure in text mode. Caught immediately by the new test below going from a confusing non-JSON CDP result to a clean pass once diagnosed; fixed by moving the declaration above the `try`. Recorded here because it's a direct, current illustration of why this project verifies against the real running page instead of trusting code review alone (see `tests/README.md`'s own stated rationale).

## Entry 30 — Entry 29's exact predicted risk, confirmed real: Cloudflare's API has no CORS support, fixed with a server-side proxy

Within minutes of the user configuring real Gemini, Groq, and Cloudflare credentials, a real failure came back verbatim: `"⚠️ All configured AI providers are unavailable right now. Gemini: Gemini is rate-limited — please wait about 59 seconds and try again. Groq: Rate limit reached — please wait about 1465 seconds and try again. Cloudflare: No internet connection reaching Cloudflare."` Two things worth separating here: Gemini and Groq's real rate limits firing is expected and the 3-provider fallback chain built in Entries 26-29 is visibly working exactly as designed (all three genuinely attempted, all three real messages surfaced honestly). The Cloudflare line is the actual bug — and it is precisely the risk Entry 29's own "HONESTY NOTE" flagged as unverified.

**Root cause, confirmed**: "No internet connection reaching Cloudflare" is misleading — the same request had just gotten real responses from Gemini and Groq, so internet connectivity was never the issue. Researched directly: `api.cloudflare.com` (Cloudflare's account/control-plane REST API, which `callCloudflare()` was calling straight from the browser) sends no CORS headers for arbitrary origins. A browser's `fetch()` to a CORS-blocked endpoint fails with the exact same generic error shape as a real network outage — indistinguishable from JavaScript's perspective, which is why `callCloudflare()`'s catch block produced a technically-accurate-sounding but substantively wrong message. This is a real architectural gap, not a credentials or config mistake: no client-side code can make a browser bypass CORS, so Entry 29's direct-to-Cloudflare approach could never have worked from any browser, for any user, regardless of how correctly the account ID/token were entered.

**The actual fix — a server-side proxy, following this project's own existing pattern**: added `drishti-web/api/cloudflare.js`, structurally mirroring the already-working `api/groq.js` proxy (server-to-server calls aren't subject to CORS; the proxy attaches the CORS headers the browser needs on the way back). One deliberate design difference from `groq.js`: Groq's proxy exists to hide the *site owner's* shared key from visitors, so it only ever uses `process.env.GROQ_API_KEY`. Cloudflare's proxy has no secret of its own by default — every visitor already pastes their *own* personal Account ID + Token into Settings (there was never a "hide the owner's key" motivation for Cloudflare specifically), so the proxy relays whatever credentials it's given: a site owner's `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_API_TOKEN` env vars if configured (matching Groq's zero-setup story), falling back to the calling visitor's own credentials sent via `X-CF-Account`/`X-CF-Token` headers otherwise. This means Cloudflare now has two independent ways to work — either the site owner sets it up once for everyone, or any individual visitor pastes their own free account — whichever is available.

**Client-side changes**: `callCloudflare()` now posts to `/api/cloudflare` (same-origin, never CORS-blocked) instead of `api.cloudflare.com` directly, sending this visitor's credentials as headers only when they've actually configured any. A new `cfProxyReady` flag (health-checked via GET on page load, exactly mirroring `groqProxyReady`/`sarvamProxyReady`'s existing pattern in `checkProxies()`) tracks whether the proxy is even reachable at all — true only on a deployment that runs serverless functions (Vercel, per this repo's `vercel.json`); false on plain static hosting (GitHub Pages, Netlify drop, `npx serve`, or opening `index.html` directly), where Cloudflare's fallback genuinely cannot be reached from a browser no matter what. `callGroq()`'s trigger condition for attempting Cloudflare changed from "visitor has personal credentials" to "visitor has personal credentials OR the proxy is confirmed reachable" — covering the zero-setup case where a visitor entered nothing but the site owner configured env vars. When the proxy isn't reachable at all, `callCloudflare()` now says exactly that ("needs the serverless proxy, which only runs once deployed to Vercel") instead of the old misleading network-failure message.

**Files touched**: `drishti-web/api/cloudflare.js` (new), `drishti-web/index.html` (`cfProxyReady` state; `checkProxies()`'s new health check; `callCloudflare()` rewritten to route through the proxy; `callGroq()`'s Cloudflare-attempt trigger condition).

**How it was verified**: `tests/test_cloudflare_fallback.mjs` (4/4, unchanged from Entry 29 — still pure control-flow logic via function-stubbing, so the proxy rewrite underneath didn't need new stub-level tests) re-run clean, confirming the fallback ordering/messaging logic is undisturbed by the routing change. `test_provider_priority.mjs` (4/4), `test_gemini_budget_and_ocr_fallback.mjs` (5/5), and `test_resilience.mjs` (11/11) re-run clean. Full regression sweep re-run clean (zero issues, all 13 modes). `node --check` confirmed `api/cloudflare.js`'s syntax is valid and structurally consistent with the already-deployed, already-working `api/groq.js`. **What was NOT verified**: this session still has no real Cloudflare account, and more importantly no way to run a real Vercel serverless function locally — so whether `api/cloudflare.js` actually resolves the CORS failure once deployed remains unconfirmed by an actual live request. This is a smaller, more confidently-scoped gap than Entry 29's original one (the CORS diagnosis itself is well-established, standard behavior, not a guess about Cloudflare's specific request/response shape, which Entry 29 already got right per the user's own error message correctly reflecting real Cloudflare error text), but it's still real: the honest status is "should fix it once deployed," not "confirmed fixed."

**Known limitations**: Cloudflare's fallback remains completely unreachable on any deployment that doesn't run serverless functions (GitHub Pages, Netlify's plain static drop, local `npx serve`, or `file://`) — this is a hard platform constraint, not a bug, and the app now says so plainly when it applies rather than presenting a confusing generic failure. ## Entry 32 — A real voice-command bug and a real Objects-mode accuracy problem, both found from live usage after the rebuild

The user reported three things after actually using the rebuilt app: "not recognizing objects very well," "does not show distance clearly," and — despite Voice Commands showing ON — "no input is given even after i speak." All three were investigated for real root causes, not guessed at.

### Voice commands going permanently silent — a real bug, found by reading the code, not by reproducing it live

**Root cause**: `vcPaused` (set `true` in `speak()` to stop the command mic hearing Drishti's own voice, meant to be reset `false` once speech finishes) had exactly one reset path: the TTS completion callback (`onDone()`) inside `speak()`. If that callback never fires — a browser autoplay-policy block on programmatic `speechSynthesis.speak()`, a Web Speech `onend` event that silently never arrives (a known category of Chrome bug this project has already hit once, Entry 13), a hung Sarvam network request — `vcPaused` stays `true` forever. `_launchCmdRec()` checks `vcPaused` before ever starting a new recognition instance, so the mic genuinely never listens again — while the "Commands: ON" button keeps showing on, since button state and this internal flag were never linked. This exactly matches the report: visibly listening, never actually hearing anything, with no error surfaced anywhere.

**The fix**: a new `vcPausedAt` timestamp, set alongside `vcPaused=true` in `speak()`. `_launchCmdRec()` now checks how long `vcPaused` has been true — under 20 seconds (comfortably longer than any real utterance this app produces, chunking included) it defers normally as before; past 20 seconds, it force-clears `vcPaused` and `isSpeaking`, logs a system message explaining what happened, and proceeds to actually restart recognition. This is a self-healing safety net, not a fix for whatever originally stalls the TTS chain (that root cause — which specific browser/network condition stalls it — remains unconfirmed, since it wasn't reproduced live this session) — but it guarantees voice commands always recover on their own instead of staying silently broken until the user notices and manually toggles the button off and on.

**Files touched**: `drishti-web/index.html` (`vcPausedAt` state; `speak()` sets it; `_launchCmdRec()`'s new recovery branch).

**How it was verified**: directly, in a real running instance of the app (not headless CDP, which was unreliable in this environment by this point in a very long session — see below) — set `vcPaused=true` with `vcPausedAt` 25 seconds in the past, called the real `_launchCmdRec()`, and confirmed it immediately cleared `vcPaused` and logged the expected recovery message. A second check with `vcPausedAt` only 2 seconds in the past confirmed the normal case is unaffected — `vcPaused` correctly stays `true` and recognition is deferred, not force-reset. Both are the real function, not a reimplementation.

### Objects mode: grounded in the real on-device detector instead of asking a vision model to guess distance

**Root cause**: `PROMPTS.objects` asks whatever vision model answers it to state "approximate distance in meters" for every object from a single 2D photo — monocular distance estimation without known camera/object-size priors isn't something any general-purpose vision-language model can do reliably, cloud or local; Entry 30's smaller local model made the resulting guesswork far more noticeable, but the underlying design problem predates it. Meanwhile this project already has a real, deterministic, already-tested local pipeline for exactly this — the on-device COCO-SSD object detector plus `bboxClockPosition()`/`proximityFromBbox()` (clock position + VERY_CLOSE/CLOSE/MEDIUM/FAR buckets) — running continuously in the background the whole time the camera is on, already backing Guardian Mode's hazard detection, but never wired into Objects mode itself.

**The fix**: Objects mode's `snap()` branch now builds its answer directly from `environmentState.objects` (the same live data Guardian Mode already uses) whenever the on-device detector has anything in frame — real detected object classes, real clock positions, real proximity buckets, sorted nearest-first — instead of asking any vision model (local or cloud) to freely guess. Only falls through to the model when there's genuinely nothing detected, or in `CLOUD_ENHANCED` mode (matching the existing pattern already established for Color mode's local shortcut). Price-estimate commentary (which the old prompt also asked for) is dropped from this local path — a deliberate scope choice, since a price guess from a photo is exactly the same kind of unreliable guesswork this fix is meant to eliminate, not something worth re-adding via a different guesser.

**Files touched**: `drishti-web/index.html` (`snap()`'s new Objects-mode branch).

**How it was verified**: directly, with a synthetic `environmentState.objects` array matching the exact real shape `buildEnvironmentState()` produces (three objects, spanning all proximity buckets), run through the actual new formatting code. Real output: *"I can see a bottle at your 12 o'clock, very close; a person at your 11 o'clock, fairly close; a chair at your 3 o'clock, far away."* — correctly sorted nearest-first, using real clock positions and real proximity language, not a guess.

## Entry 34 — The local model was never actually reachable from Hybrid mode: a real, high-impact gap, found from a real screenshot

The user asked "is the 2B model ready?" and, in the course of answering, sent a real screenshot of the live app. It showed something more important than the 2B model's status: the user's browser is on **Hybrid mode** (their own saved preference from before Entry 30 ever shipped — `aiMode`'s default only changes what a brand-new visitor with empty `localStorage` starts on, and this user already had a saved value), with a real Groq key configured. Not a local-model answer. An error.

**Root cause**: `callGroq()`'s local-model path was gated on `aiMode==='LOCAL_ONLY'` only, checked once at the very top of the function. Every caller who wasn't in that exact mode — which, per the reasoning above, is most real returning users — had no path to the local model at all, no matter how completely the cloud side failed. All of Entries 30, 32, and 33's real work (a working local VLM, verified producing real coherent output, upgraded for better accuracy) was unreachable from the mode most actual users are in. This is very plausibly what was really behind at least some of the earlier "still not working" reports too — those may have been testing whatever mode happened to be saved in that browser tab, not necessarily the local-only path being discussed.

**The fix**: `callGroq()` now tries the local model as a genuine fourth-tier, last-resort fallback — after Gemini, Groq, and Cloudflare have all been attempted and failed, in *any* mode except `CLOUD_ENHANCED` (which exists specifically to force every request through the cloud for research/comparison, per its own original definition — silently substituting a local answer there would defeat the point of choosing it). If the local model also fails (not loaded, no WebGPU, etc.), the original real combined cloud-provider error still surfaces exactly as before — a local failure never hides what actually happened on the cloud side.

**A deliberate choice, not an oversight**: the local model is NOT pre-warmed (loaded in the background) for Hybrid-mode visitors the way it is for Local-Only visitors, even though this fallback now exists. Pre-loading a multi-gigabyte model for every visitor whose cloud APIs are working fine would waste real bandwidth for the common case. The tradeoff: the *first* time this fallback actually fires in a session, there's a real wait for the model to download — mitigated by the existing "🧠 Loading the local vision model..." message already firing in that path (from `loadLocalVLM()`, unchanged), so the wait is explained, not silent.

**How it was verified**: directly, against the real running app (not a reimplementation) — three real scenarios, matching the exact shape of the user's screenshot: (1) Gemini and Groq both stubbed to fail, no Cloudflare configured, `aiMode='HYBRID'` — the real `callGroq()` correctly reached and returned the local model's real result, with a clear system message explaining the fallback fired; (2) the same failure, but with the local model *also* stubbed to fail — confirmed the original honest combined error ("All configured AI providers are unavailable right now. Gemini: ... Groq: ...") still surfaces unchanged, not swallowed; (3) the identical failure in `aiMode='CLOUD_ENHANCED'` — confirmed the local model is never even called, and the same honest cloud error surfaces, matching that mode's own stated purpose.

**Files touched**: `drishti-web/index.html` (`callGroq()`'s new fourth fallback tier, inserted between the Cloudflare attempt and the final combined-error throw).

**Known limitations**: this fixes reachability — the local model can now actually be reached from the mode most real users are in — but does not change anything about the model's own accuracy (see Entry 32/33's already-documented, disclosed quality ceiling). A user whose cloud providers are all genuinely down will now get *a* real, on-device answer instead of an error, which is strictly better, but that answer carries the same real accuracy limitations already documented, not cloud-equivalent quality.

Genuinely local, zero extra cost, and directly answers the exact two things the small model itself cannot: real distance/position and real color. Scoped deliberately to Describe mode only (the mode with the reported complaint) and only when `environmentState.objects` actually has real detections — no detections means no fabricated addition, matching this project's standing "never guess" rule.

**Files touched**: `drishti-web/index.html` (`callLocalVLM()`'s enrichment step), `drishti-web/tests/test_local_describe_enrichment.mjs` (new).
