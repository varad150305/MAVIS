# Drishti web — test suite

**`check_tdz.mjs`** — run this first, always: `node tests/check_tdz.mjs index.html`. It's a static analysis tool, not a CDP-driven test (no server/Chrome needed), that catches the specific bug class that broke this app three separate times this session: a top-level `let`/`const` used (in code that runs immediately on page load) before its declaration line. Each time, the fix was in a completely different variable (`vcOn`, `snapHistory`, `aiMode`) and each time it silently killed the entire script — every button, every mode, everything — because JavaScript's temporal dead zone throws at the point of use, and nothing after that point in a single `<script>` block ever runs. A human re-reading the list of top-level statements missed it every time, including the person who introduced the third instance while writing this very sentence's fix. Run it after any change that adds a new top-level `let`/`const` or a new top-level statement that runs during page load.

These aren't unit tests in the Jest sense — they drive the *actual running app* inside a real Chrome instance via the Chrome DevTools Protocol (CDP), the same way a human would (click buttons, switch modes, evaluate real functions), then check real return values and catch real thrown exceptions. This exists because two serious bugs this project shipped with (both crashing the entire script on load — see `IMPLEMENTATION_PROGRESS.md`) were invisible to code review and only surfaced by actually running the page.

## What's here

- **`test_hazard_engine.mjs`** — 20 deterministic checks against the local Environment State / Object Tracking / Hazard Engine / Priority Engine (clock-position mapping, proximity bucketing, path-corridor detection, tracking continuity + motion classification, hazard risk scoring, priority-engine dedup and the Guardian-mode gate). No network, no camera, no LLM — pure logic, verified by evaluating the real functions with synthetic detections.
- **`test_color_engine.mjs`** — 16 deterministic checks against local color detection (nearest-color-name mapping for every primary/secondary color, and the 3×3 dominant-color grid against a canvas painted with known colors).
- **`test_full_regression_sweep.mjs`** — drives every mode (all 13), every toggle (Smart Live, Guardian, Wake Word, Large Text), voice-command parsing, history, chat/Q&A, SOS, sharing, and the phone modal, with the Groq network call intercepted and stubbed (via CDP `Fetch` domain) so this runs fully offline/free and checks for any uncaught exception or console error across the whole app in one pass.
- **`test_crossing_mode.mjs`** — 10 checks that Crossing mode never speaks or displays a GO/WAIT-style verdict, never speaks the raw `CLEAR_VIEW`/`UNCLEAR_VIEW` marker token, and always includes the safety disclaimer — including a defense-in-depth case where the mocked model returns an old-style `GO` verdict anyway, to confirm the app doesn't just trust the prompt.
- **`test_ocr_engine.mjs`** — 5 checks against the *real* Tesseract.js OCR engine (not a mock): renders actual text onto a canvas via the Canvas API and confirms the real engine reads it back with a confidence score above the app's threshold, plus confirms a blank canvas doesn't produce fabricated text. Downloads Tesseract's WASM binary + language data on first run — can take up to a minute.
- **`test_currency_engine.mjs`** — 10 checks against local currency recognition (OCR + color heuristic, not a trained classifier): pure-logic denomination-extraction edge cases (serial-number false positives, ₹100 vs ₹1000 word-boundary confusion, picking the most-frequent candidate), then two full real-OCR runs against a synthetic "note" — matching number+color correctly reaches HIGH confidence, mismatched color correctly demotes to MEDIUM (meaning the real app falls back to the cloud model rather than guess).
- **`test_resilience.mjs`** — 11 checks added after real-API-key testing (and real live usage) surfaced real bugs (see `IMPLEMENTATION_PROGRESS.md` Entries 10-12): the truncation-retry logic in `callGroq()`, adaptive object-detector downgrading, rate-limit message parsing, the retry/fallback failure paths reusing that same message parsing (they didn't, originally — a bare "Groq error 429" instead), and — found by the user during actual usage, not by any test — Guardian Mode's cooldown genuinely pacing every attempt (it previously only reset on an actual alert, so a persistent hazard rated SAFE would hammer the API on almost every detection tick).
- **`test_speech_chunking.mjs`** — 8 checks for one of two bugs behind "only reads the first few lines then stops" (see `IMPLEMENTATION_PROGRESS.md` Entry 13): confirms long text actually splits into multiple sentence-complete chunks with no words lost, confirms **all** chunks get queued for speech (not just the first), and confirms a cancelled/superseded speech chain genuinely stops rather than continuing to talk.
- **`test_followup_timing.mjs`** — 4 checks for the *other*, actually-primary cause of the same symptom (Entry 14): a proactive "I can see text, say read it" follow-up used to fire on a guessed 8-second-capped timer instead of waiting for the real description to finish speaking — for any description of real length this cut the main description off partway. Uses a mocked `speak()` that takes a realistic ~3s to "finish" (an instant mock would never expose this) to confirm the follow-up now only starts after the real completion callback fires, never on a guess.
- **`test_depth_engine.mjs`** — 7 fast deterministic checks against the real monocular depth-estimation module's logic (coordinate-scaled sampling, relative-percentile bucketing, safe fallback when the model is unavailable), plus 1 slow but genuinely real end-to-end run of the actual depth model (`Xenova/depth-anything-small-hf` via Transformers.js — downloads on first run, can take 30-90s) confirming it correctly ranks a near region as closer than a far one. Pass `--skip-real` to skip the slow real-model run for quick iteration.
- **`test_local_grounding.mjs`** — 7 checks that Objects mode and Prices mode both ground their answer in real on-device COCO-SSD detections instead of asking any vision model to guess distance or price from a single photo (neither is something a photo alone can determine) — confirms `localObjectSummary()`'s nearest-first output, confirms Prices mode's answer never contains a ₹ symbol or an "Rs" mention, confirms both `PROMPTS.objects`/`PROMPTS.prices` no longer ask for a price, and confirms `CLOUD_ENHANCED` mode never uses the local branch for either. Pure logic, no camera/network/LLM needed.
- **`test_sound_classifier.mjs`** — 6 fast deterministic checks against the local sound-hazard classifier's allowlist/threshold/cooldown logic (YAMNet class-index mapping, cooldown suppression for a repeated sound, independent cooldowns per sound class, no fabricated direction claims), plus 1 slow but genuinely real end-to-end run of the actual YAMNet model confirming the real, documented output shape (`[N,521]` scores + embeddings + spectrogram). Pass `--skip-real` to skip the slow real-model run. **Full audio-pipeline verification (real mic capture → resample → inference → announcement → cooldown) was done manually** via `--use-file-for-fake-audio-capture` (see below) rather than as an automated test, since it needs a WAV fixture path that isn't portable across environments — see `IMPLEMENTATION_PROGRESS.md`'s local-ML entry for the real scores this produced.

## How to run

1. Serve the app locally: `npx serve . -l 5000` from `drishti-web/`.
2. Launch Chrome with remote debugging and a fake camera device (headless or not):
   ```
   chrome --headless=new --disable-gpu --remote-debugging-port=9333 \
     --use-fake-device-for-media-stream --use-fake-ui-for-media-stream \
     --autoplay-policy=no-user-gesture-required --user-data-dir=/tmp/drishti-test-profile
   ```
3. `node tests/test_hazard_engine.mjs` (or any of the others). Each prints PASS/FAIL per check and exits non-zero on any failure — wire this into CI as-is.
4. **Restart the Chrome instance periodically** (every ~10-15 test runs, or if a run hangs with no output). Each run opens a fresh tab via `/json/new` and never closes it — after enough accumulate in one long-lived Chrome process, it degrades and requests intermittently hang. Killing and relaunching Chrome is the fix; this isn't a bug in the app or the tests.
5. **For real audio testing** (`test_sound_classifier.mjs`'s manual end-to-end verification, or any future audio test): add `--use-file-for-fake-audio-capture=<path-to.wav>` to the launch command above — it loops a real WAV file as the fake microphone's input instead of silence, the audio equivalent of `--use-fake-device-for-media-stream` for video. A synthetic siren needs a **continuous smooth frequency sweep** (glissando), not discrete alternating tones, to be recognized as "Siren"/"Alarm" by YAMNet — a first attempt using abrupt two-tone switching read to the model as a synthesizer/beep instead (see `IMPLEMENTATION_PROGRESS.md`'s local-ML entry for the real scores from both attempts).

## A gotcha that actually bit this project — read before adding a new mocked-network test

If you intercept a `fetch()` to a cross-origin HTTPS endpoint via CDP's `Fetch` domain, **`Fetch.requestPaused` fires for the CORS preflight `OPTIONS` request before it ever fires for the real `POST`** (any POST with a JSON body triggers one). If you fulfill that OPTIONS request without `Access-Control-Allow-Origin`/`-Methods`/`-Headers`, the browser correctly treats the preflight as failed and silently blocks the real POST — the page's `fetch()` rejects with "Failed to fetch", and if the app's own error handling swallows that (as this app's `snap()` does, by design, so a network blip doesn't crash the UI), **a test that only checks for uncaught exceptions will report a false pass while never actually exercising the mocked success path.** This happened for real in this project — see `IMPLEMENTATION_PROGRESS.md` Entry 4. Always check `request.method` and handle `OPTIONS` separately with proper CORS headers, and assert on actual rendered content at least once per new test, not just "did it crash."

## Why this approach instead of a mocking framework

The app is deliberately a single dependency-free `index.html` with no build step (see the project README's own "deploy anywhere" philosophy) — introducing a bundler/test framework just to unit-test in isolation would work against that design choice. Driving the real page via CDP tests the actual deployed artifact, not a reimplementation of its logic, at the cost of needing a real Chrome + local server rather than `npm test` in a plain Node process.
